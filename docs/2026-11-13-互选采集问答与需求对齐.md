# 互选采集问答与需求对齐

记录日期：2026-11-13（北京时间）。覆盖本会话的目标澄清、运行反馈及两轮端点问答。关联 [FAI-920](https://linear.app/fxxkai/issue/FAI-920)、[FAI-912](https://linear.app/fxxkai/issue/FAI-912)、[FAI-916](https://linear.app/fxxkai/issue/FAI-916)。

本文是讨论记录与事实台账。用户原问保留原意；“当时答复摘要”记录此前说法，“本轮核验”补充依据和更正。实现、静态源码、真实网页抓包及最终入库验收分别标明。后续问答继续追加，发生更正时同时保留原说法和原因。

## 一、用户明确的目标

> 我要的是高效、避免风控的采集筛选后的达人信息。达人信息分为列表和达人主页。

- 使用用户在腾讯互选创作者广场已经生效的账号、筛选和排序。
- 列表与主页是两个取数层次，列表请求可批量取得一页作者字段。
- 按已确认范围完整采集主页与作品；“接口已实现”“响应已保留”“研究台已正确解析展示”分别验收。
- 通过真实网页请求、一手源码及合理节奏确认请求编排；不以任意串行等待代替平台行为核验，也不将并发等同于不受限。
- 原始单位、区间、缺失状态和来源保留，粉丝画像与观众画像分开。

## 二、前期问答与已确认边界

### 1. 为什么显示筛选或账号变化，需要结束重开？

**用户纠正：** 用户没有要求禁止同轮切换筛选或广告账号。

**对齐结果：** 同轮可以采用新条件继续采集，已有结果保留。旧条件的页码不能套用到新条件。此前还有旧版与新版页面通信冲突的现场记录；不能把所有此类错误都归因于用户修改筛选。

### 2. 已上传持续增加，为什么账号、页数或最近记录不动？

**当时定位：** 完整资料页完成后才登记账号／推进页数，侧栏也未接入互选候选。上传按列表、栏目、作品分页及分段记录计数，一位达人对应多条。

**已做的本地修正：** 列表持久化后登记候选与成功列表页；单个达人完成后更新最近记录并标记“采集完成”；资料完成页另计。源码回归与 dist 构建通过，已安装插件的持续运行仍须单独验收。

### 3. 一个达人采完，就应该显示吗？

**用户要求：** 每位达人完成后立即显示，不能等待全页达人完成。

**对齐结果：** 已发现候选与真正完成资料分别表达；完成账号应立即更新到最近记录。配置范围内作品分页的耗时应能够观察，而非只显示一个长期不变的账号名。

### 4. 点击开始或继续，为什么刷新网页？

**已定位：** 后台探测不到 content 脚本时，旧恢复逻辑直接调用 `chrome.tabs.reload`。

**对齐结果：** 已打开互选时复用用户当前页面，不刷新；断连在原页恢复脚本，保留已捕获筛选。没有打开时才打开。首页／登录准备状态与跨窗口复用仍是需要单独核验的边界，不能仅凭打开辅助函数测试通过宣称完整使用流程已通过。

### 5. 继续时网页显示页码与保存断点不一致，采用哪个？

**用户明确回答：** “从已保存断点继续，沿用当前筛选”。

**对齐结果：** 条件未变时恢复保存断点，包括未完成的达人、栏目和作品页。账号／筛选／排序改变时按当前新条件获取列表，本轮旧结果保留。接口翻页不会自动改变网页可见分页。

### 6. 为什么体感一个达人需要一分钟？

**修复前的代码事实：** 串行执行8个资料请求，再遍历近180天的发表视频和商单作品分页；每个外部请求保存后都等待 `huxuanDelay`。两类作品各只有1页时，也有10次请求。

**修复前4—6秒设置下的推算：** 每人仅等待即40—60秒，另加响应与保存时间；30人一页仅等待约20—30分钟。作品页更多则更久。这是代码推算，不是当前“歪果仁研究协会”账号的实时请求测量。

**误判更正：** 用户预期的是“每位达人之间的可配置间隔”。此前把该设置施加到每个端点，是实现与需求不一致。不能靠追加解释文字宣称配置已正确交付。

### 7. 版本号、更新页与交付

**用户要求：** 更新版本号和更新页。

**本地记录：** 前一轮更新至1.1.31，本轮修正更新至1.1.32；更新页、生成的版本记录和 dist 同步。测试／构建属于本地验证，不能代替已安装插件、实际请求、上传处理和研究台展示验收。Git提交、推送及商店发布按用户另行授权执行。

## 三、第一轮六个问题

### Q1. 我们达人主页的信息采集全了吗？包括受众画像和达人主页？

**当时答复摘要：** 已覆盖此前调研的主页栏目，包括 `detail.user_profile` 粉丝画像与 `detail.viewer_profile` 观众画像；此前真实抽样两位达人，不能据此保证所有账号所有字段都已完整验收。

**本轮核验：** `detail` 的两套画像读取可由腾讯3.278.1静态源码证实。插件保存接口返回的全部业务字段；缺失／无权限仍须分别记录。详情见 [端点审计](research/2026-11-13-huxuan-endpoint-audit.md) 与 [既有完整采集验收](verification/2026-11-10-huxuan-full-profile.md)。

### Q2. 用户点击某个达人主页，是否也同时请求这么多端点？

**当时答复摘要：** 会涉及多个请求，但不能把打开主页等同于插件当前遍历全部近180天作品分页；最新网页准确请求数及并发顺序未重新抓包确认。

**本轮核验：** 已重新取得腾讯公开前端静态源码，按组件初始化、类型切换和分页回调定位调用关系。当前登录网页的网络瀑布尚未取得。不能将用户关于同时加载的描述、静态组件结构或插件自己的调用日志写成“已实测官网同时请求全部端点”。

### Q3. 之前调研的主页端点全了吗？会有一个汇总的吗？

**当时答复摘要：** 已覆盖此前调研范围，未证明全部端点穷尽；`detail` 已聚合基础资料、表现及两套画像，未确认单接口覆盖全部主页栏目和全部作品。

**本轮核验：** 已追加公开官方源码与开源检索。端点清单必须区分主页初始请求、切换栏目请求、列表翻页、作品翻页和二级详情；详见端点审计。检索无结果不等于证明接口不存在。

### Q4. 用户打开主页会请求多个端点，为什么一个个间隔几秒？最开始预计每个达人主页之间有可配置时间。

**当时答复摘要：** 这是我对间隔作用对象的错误理解。正确意图是按一位达人的必要请求组成一组，在切换下一位达人前执行可配置间隔。

**修复结果：** 1.1.32移除逐接口等待，同页相邻未完成达人之间执行一次达人间隔。确认detail身份后独立栏目并行，所有保存完成后才推进；同时只采一位达人。旧页面桥接不支持并行时保留当前筛选、顺序请求，同样移除逐接口等待。官网现网请求瀑布仍待浏览器连接恢复后核验。

### Q5. 翻页是不是也要请求一个端点？

**当时答复摘要：** 是。列表翻页继续调用 `POST /cgi-bin/advertiser/finder_publisher/search`，改 `page.no`，保留账号、筛选、排序与每页数量。

**边界：** 列表分页与作品分页是不同对象；作品使用 `get_finder_video_show` 及 `page_index`。

### Q6. 列表端点是不是一次获取30个达人的列表字段？

**当时答复摘要：** 是。网站当前 `page.size=30` 时一次返回最多30位（末页可能不足），每位作者的全部业务字段保存在 `listFields`。这不包含所有主页与作品数据。

**已有证据：** 2026-10-24真实验证两页各30位、合计60个不同 `appid`；2026-11-10真实列表样本保留119个业务字段。样本数量与字段覆盖不是对未来所有响应的固定承诺。

## 四、第二轮六个问题（本次追加）

### Q1. 既然用户打开主页时同时获取端点，为什么想到一个个打？不确定为什么不抓包？

**答复：** 此前没有先完成同场景的官网请求对照，就采用逐接口串行等待，缺少证据依据。此前完成的取数抽样不等于官网首次打开页面的网络瀑布。

**本轮动作与结果：** 2026-11-13再次尝试连接真实浏览器，返回 `Sky Computer Use native pipe startup failed` 和 `The browser access host is unavailable`，没有可用浏览器标签。没有刷新、重开或操作用户当前采集任务。已用可访问的官方静态源码补充调用关系审计；当前登录网页抓包仍为明确缺口。

### Q2. 未证明端点穷尽，是否应该进一步定位、检索开源项目，保证努力获取过？

**答复：** 应当。本轮已重新检索官方源码和GitHub一手实现，记录搜索词、实际命中、维护状态、可复用范围及未能证明的事项，详见 [端点审计](research/2026-11-13-huxuan-endpoint-audit.md)。普通视频号客户端／视频下载器不能直接当作互选广告市场接口实现。

### Q3. detail 已包含部分信息，是否判断过与其他端点字段重复？

**答复：** 此前未完成同账号、同时间窗的逐字段差异审计，这是缺口。

**本轮发现：** 腾讯旧版源码中，`near_videos` 一次ALL响应携带 `personal_video_data`、`order_video_data`，趋势类型切换使用响应中的数据。插件当前额外调用 `near:3` 与 `near:1`，应优先核对能否省掉。该证据尚不等于证明 `detail` 与所有额外接口完全等价。

**比较规则：** 逐字段比较身份、参数、时间窗、内容类型、值与权限。粉丝画像和观众画像即使维度同名也不是重复；近30条趋势与近180天作品列表也不直接等价。详情响应与列表中的身份／报价等字段还须比较实际同账号响应，不能只看字段名删请求。

### Q4. 一页最后一个达人获取完成后，不应该等时间后再翻页吗？

**答复：** 应当把它作为明确的“列表翻页间隔”。

**修复结果：** 全页资料保存完成且获准继续后，使用独立翻页区间等待，再获取下一列表页。页边界不叠加达人等待。作品连续分页也使用翻页区间，避免大量作品无间隔连发；栏目首页不额外等待。

### Q5. 能确信视频字段、封面等也获取了吗？

**答复：** 现有代码具备原始字段保留与上传路径；腾讯旧版页面明确读取 `export_id`、`description`、`publish_time`、`cover_url`、`video_url`、播放／两类赞／评论／转发等字段。工作台解析器也显式映射 `cover_url`、`video_url` 及已返回时长字段。

**验收边界：** 这只能证明字段合同和代码路径，不能证明当前账号每条作品字段都有值、签名媒体地址持续可用、全部作品已完成上传解析。保留封面URL不等于下载了封面文件；保留视频URL不等于下载视频文件。需要用当前同账号样本逐字段核对原响应→本地记录→上传接收→研究台事实／展示。

**本轮已执行的字段通路检查：** 使用明确标记的合成作品样例，调用真实 `huxuanCaptureRows` → `normalizeHuxuanObservation` → `huxuanObservationRecord` → `parseHuxuanWork`。原始作品对象在上传载荷内逐值保留，封面URL、视频URL与42秒时长分别解析正确。此检查没有发起真实上传，没有验证当前账号的作品已入库，也没有访问或下载媒体文件。

### Q6. 最开始就要求时间在运行设置有输入，可自由配置，而不是代码写死。

**原问题：** 原输入作用在每个接口后且共用区间，粒度错误。

**修复结果：** 运行设置提供达人间隔、列表及作品翻页间隔的四个实际输入，保存、回读、运行参数已接通。支持0秒及超过30秒，校验非负有限数和上下界；长等待分段保活且可暂停。当前运行显示本轮参数，保存供下一轮使用，续跑沿用本轮参数。

**用户目标：** 运行设置应明确提供达人之间等待与列表翻页前等待，输入保存后控制真实执行。每类时间的最短／最长、当前生效值及保存后的生效时机应一致；默认值是初始值，不能代替用户设置。此前1—30秒硬上限缺少业务依据，本轮已移除。

**状态：** 1.1.32已完成代码与配置修正，本地验证见下节。真实抓包、逐字段同账号对照、已安装页面和入库验收仍受浏览器连接阻塞，不能称为现网验收通过。
